# 나의 트레이딩

Next.js 소유자 전용 웹 화면과 Vercel Workflow 예약 실행으로 PC를 꺼도 봇을 실행하는 프로젝트입니다. 최초 설정은 **모의거래**입니다.

## 실행 구조

1. 로그인한 소유자가 웹에서 시작합니다.
2. Vercel Workflow가 바이낸스 BTCUSDT 15분 봉을 조회하고 처리합니다.
3. 처리 상태·거래·키는 PostgreSQL에 저장합니다. 재배포 후에도 유지됩니다.
4. 다음 봉 마감 5초 후까지 영구 예약으로 대기하고 새 실행을 시작합니다. 대기 중 PC나 브라우저가 필요하지 않습니다.

반복 Cron 설정이나 별도 VPS는 필요하지 않습니다. 예약 실행은 실시간 보장이 없으며, 지연된 신호는 신규 진입을 생략합니다. 실주문 모드에서는 손절·익절을 바이낸스 거래소의 조건부 주문으로 등록합니다.

## Vercel 배포

저장소를 Vercel에서 가져오고 Next.js 프리셋, 루트 `./`, Node 24를 사용합니다. `vercel.json`은 서울 실행 지역을 지정합니다. PostgreSQL을 생성하여 연결합니다. 무료 플랜에서도 사용량 한도와 거래소 접근 가능 여부를 확인해야 하며, 한도 초과·장애로 실행이 중지될 수 있습니다.

운영 환경 변수:

| 변수 | 값 |
| --- | --- |
| `DATABASE_URL` | TLS 연결이 설정된 영구 PostgreSQL 주소 |
| `ADMIN_PASSWORD_HASH` | `npm run setup`으로 생성한 scrypt 비밀번호 해시 |
| `CREDENTIAL_ENCRYPTION_KEY` | 같은 명령으로 생성한 32바이트 base64 키. 보관하고 재배포 때 유지 |
| `APP_ORIGIN` | 실제 웹 주소, 예: `https://bi-xxx.vercel.app` |
| `BOT_TRADING_MODE` | 최초 `paper` |
| `ALLOW_MAINNET_LIVE` | 최초 `false` |

실제 값은 GitHub, 이 문서, 화면 캡처, 채팅에 올리지 않습니다. `NEXT_PUBLIC_` 환경 변수로 설정하지 않습니다. 운영 DB와 비밀 값은 Production에만 넣습니다. Preview에 운영 자격증명을 공유하지 않습니다.

로컬 준비: `npm ci`, `npm run setup`, `npm run dev`. `.local/owner-access.txt`의 비밀번호로 로그인합니다. 이미 `.env.local`이 있으면 setup은 보존합니다. 로컬 SQLite는 개발용이며 Vercel에서는 사용하지 않습니다.

배포 후 로그인 → 모의거래 시작 → 최근 실행과 다음 예약 확인 → 웹을 닫은 뒤 다음 봉 이후 재접속하여 실행이 이어졌는지 확인합니다. Vercel Workflow 목록에서도 예약을 확인할 수 있습니다. 웹을 열었을 때만 실행되는 구조가 아닙니다.

## API 키 저장 위치

웹의 **API 키 관리**에서 테스트 또는 실계정 키를 입력하고 **암호화하여 저장**을 누릅니다. AES-256-GCM으로 서버에서 암호화해 DB에 저장하며, 로그아웃과 재배포 후에도 유지됩니다. 브라우저에는 마스킹된 키만 반환합니다. Workflow 입력/결과에도 키를 넣지 않습니다. 암호화 키를 잃으면 저장된 API 키를 복구할 수 없습니다.

키 저장만으로 실주문은 시작되지 않습니다. 테스트 계정 모드는 `BOT_TRADING_MODE=testnet`, 실계정은 `mainnet`과 `ALLOW_MAINNET_LIVE=true`를 운영 설정에 적용한 뒤 재배포해야 합니다. 주문 모드의 시작에는 화면의 추가 확인 문구가 필요합니다. 실계정 전환 전에 Demo 체결·손절·익절을 실제로 검증해야 합니다. 출금 권한은 사용하지 않습니다. IP 제한을 사용하는 키에는 Vercel의 출발 IP 조건을 별도로 충족해야 합니다.

## 중지와 복구

중지는 신규 진입을 막고 기존 포지션의 정산·보호 주문 확인 예약은 유지합니다. 보호 주문 누락 또는 청산 여유 부족을 확인하면 해당 봇 포지션을 reduce-only로 종료합니다. 키 삭제는 API 접근을 없애므로 이 감독도 불가능해집니다. 열린 포지션은 거래소에서 확인해야 합니다.

주문 전 전체 진입 계획과 고정 서명 시각을 DB에 저장합니다. 미확정 주문은 원래 client ID로 조회하며, 체결이 확인되면 기록과 보호 상태를 복구합니다. 요청 유효시간 종료 후 거래소에서 미존재 및 포지션 없음이 확인된 새 의도만 해제합니다. 이전 버전 의도는 근거가 부족하면 계속 차단합니다. 오류 화면의 **주문 상태 복구**로 감독 예약을 다시 시작할 수 있습니다. 복구 후 신규 진입은 시작 버튼으로 재개합니다. 동일 계정의 실행 잠금으로 동시 주문을 제한합니다.

계획 위험은 수수료·체결 여유를 포함해 잔고와 사용 가능 잔고 중 작은 금액의 0.5% 이내입니다. 고정 금액도 이를 초과하면 진입하지 않습니다. 실제 손실의 보장 한도는 아닙니다. 배수별 유지증거금과 체결 후 청산 가격도 확인합니다.

모의거래는 마감된 봉의 고가·저가로 청산을 판단합니다. 한 봉에서 손절·익절이 모두 닿으면 손절을 먼저 적용합니다. 기존 PC의 5초 주기 가격 감시와 결과가 동일하지 않습니다. 기본 전략 지표·점수·위험 제한을 TypeScript로 이식했으며, 기존 로컬 거래 기록을 자동 이관하지 않습니다.

검증: `npm test`, `npm run build`, `npm audit --omit=dev`. 실제 자금 주문은 검증 명령에 포함되지 않습니다.

공식 문서: [Vercel Workflow](https://useworkflow.dev/docs/foundations/starting-workflows), [Vercel 요금](https://vercel.com/pricing), [Binance USDⓈ-M API](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade).

계정 잔고: 거래 현황에서 Demo/실계정을 선택하면 USDT 지갑 잔고와 사용 가능 잔고를 조회합니다. 내부 paper 잔고/성과와 별도 표시합니다. 조회만으로 주문 모드를 변경하지 않습니다.
비밀번호 변경: 소유자 메뉴에서 현재 비밀번호와 새 비밀번호(4~128자)를 입력합니다. 해시는 DB에 저장되어 재배포 후에도 유지되며 모든 세션이 종료됩니다. ADMIN_PASSWORD_HASH는 최초 로그인용으로만 사용됩니다.


## 2026-10-23 전략 검증

`npm run research`는 공개 거래/마크 가격 15분 봉과 펀딩 기록을 내려받아 .local/research에 캐시합니다. 최근 구간(2026-04-21~10-08)과 별도 2025년 구간을 비교하며 계정 API 키는 사용하지 않습니다. 검증 엔진 회귀 테스트는 npm test에 포함됩니다.

기본 2R 전략: 최근 208회, 승률 33.17%, 평가 포함 수익률 -11.51%; 2025년 572회, 승률 33.74%, -24.84%. 자동 수량·손절 최대 1.5%, 계획 위험 0.5%(가격 대비 비용 여유 0.3% 포함), 시작 1,000 USDT, 편도 수수료 0.05% 및 슬리피지 0.02%, 과거 펀딩을 반영했습니다. 미래 성과나 사용자 실제 계정 성적이 아닙니다. 실행 지연, 청산 위험 검사, 통신 실패와 주문 유동성은 완전히 재현하지 못합니다. 수익성 있는 지표 교체 근거가 없어 진입 신호는 유지했습니다.

## 2026-11-02 지속 실행 수정

포지션이 없는 상태에서 조회·조건 확인이 실패하면 시작 의도를 보존하고 60초 후 재시도합니다. 열린 포지션의 일시 통신 오류는 30초 후 보호 상태를 먼저 재확인합니다. 미확정 주문이나 보호 상태 불일치는 신규 진입을 차단한 채 복구 확인합니다. 수동 중지·긴급 종료는 자동으로 재시작하지 않습니다. DB 단계 또는 다음 배포 실행 연결 실패 시 현재 Workflow가 대기 후 재시도합니다. 서비스 자체의 중단이나 사용량 제한까지 무중단을 보장하지는 않습니다. 이전 코드에서 이미 중지된 봇은 화면에서 시작해야 합니다.

## 2026-11-05 거래 종료 후 연속 실행

정상 손절·익절 뒤 체결·펀딩·잔여 보호 주문 정산이 지연되면 30초마다 다시 확인하며 기존 시작 상태를 유지합니다. 정산이 완료되기 전에는 신규 주문을 보내지 않습니다. 계정과 보호 주문 조회 사이에 정상 종료된 포지션은 다시 확인해 긴급 종료로 오인하지 않습니다. 정산 완료 후 다음 15분 봉부터 진입 조건을 평가합니다. 신호 대기와 일일 손실 제한의 대기 사유도 표시합니다. 강제 종료·수동 중지·실제 보호 주문 누락으로 인한 중지 상태는 자동 해제하지 않습니다. Mock 거래소 통합 테스트로 정산 지연 → 정산 완료 → 다음 봉 신규 진입·보호 주문까지 검증했습니다.

## 2026-11-05 진입 품질 및 종료 진단

기존 설정에 entryFilter가 없으면 pullback(추세·눌림목 확인)을 기본 적용합니다. settings의 baseline으로 기존 점수 방식을 선택할 수 있습니다. ADX≥25, 방향별 RSI(롱50~68/숏32~50), EMA20 이격≤1.5ATR, 직전 세 봉의 눌림목과 직전 봉 고저점 재돌파를 요구합니다. 차기 신규 진입에만 적용하며 보호 가격·배수·진입금액을 자동 변경하지 않습니다.

주문 전 현재 호가 및 마크 가격을 확인합니다. 스프레드>0.1%, 예상 체결가 이탈>min(손절 거리×25%, 가격×0.1%), 마크 괴리>min(손절 거리×50%, 가격×0.2%) 또는 마크가 보호 범위 밖이면 진입하지 않습니다. 이는 즉시 보호 발동·높은 거래 비용을 피하기 위한 보수적 검사이며 수익성 보증이 아닙니다. 종료 사유는 수동 종료, 보호 문제, 청산 여유, 거래소 종료(원인 미확정)를 구분하며 과거 거래 원인은 추정해서 덮어쓰지 않습니다.

재현 순서: npm run research → node scripts/download-quality-holdout.mjs → node --experimental-strip-types scripts/quality-strategies.mjs. 공개 데이터만 사용하며 .local/research의 결과를 검토 후 quality-results.json에 반영합니다. 250개 공개 캔들 테스트 fixture는 Binance BTCUSDT 15분 봉에서 추출했습니다.

눌림목 후보: 2025년 202건/38.61%/-4.39%, 2026.04.21~10.08 86건/38.37%/-3.56%, 2026.10.08~11.05 UTC 16건/43.75%/+0.49%. 앞 두 구간은 탐색 데이터, 마지막 구간은 후보 고정 후 확인한 표본입니다. 손실 감소와 승률 개선이 관측됐지만 장기 양의 기대수익은 검증되지 않았습니다. 실제 호가 검사는 과거 시뮬레이션에 미포함입니다.
